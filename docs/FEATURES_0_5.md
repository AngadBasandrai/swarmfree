# Swarm Workbench 0.5

Open Control room → Team & setup for the new features. Swarm Workbench remains a downloadable Tauri desktop application with a local engine, MIT source and independently allocated contributing devices. The public domain hosts package metadata and an update feed.

1. **Guided setup.** Detects each user's hardware, shows RAM/VRAM allocations, recommends a fitting local catalog model, checks installed prerequisites and tracks setup progress. Existing Hardware, Providers and Private Network panels manage allocations, Ollama downloads, GGUF imports, keys and device pairing. Verified file downloads require publisher SHA-256 and an explicit byte ceiling; HTTPS destinations and redirects are DNS-checked/pinned. Bytes with wrong hashes are discarded. Downloads never install or execute programs.
2. **Architecture copilot.** Offline role extraction generates pipeline, parallel and supervisor graphs. Connected models can propose schema-constrained graphs under mission budgets. Preview, edit JSON, validate contracts/cycles/references, then save a new custom architecture. Offline extraction names each recognized role once; edit JSON to add multiple specialists of the same role.
3. **Reusable sub-swarms.** Set a node to `subswarm` and select its saved architecture ID. Missions snapshot child graphs. Cycles, depth >2, expanded graphs >128 nodes and excess root subtasks are rejected. Child input is `{task, upstream}`; optional JSON schemas validate input and terminal output. Children inherit routes, source labels and root request/token/spend/time budgets, with tool grants intersected with the parent's grants. Parent pause also pauses active children. Interrupted children reuse their saved checkpoints.
4. **Agent channels.** Architectures declare channels with member node IDs and message ceilings. `agent.send`, `agent.inbox`, `agent.claim` require normal project/agent tool grants. Peer messages are labeled as data, preserve provenance and consume node/channel budgets. Task claims are atomic and first-owner wins. Owner UI can inspect conversations and inject a message as a selected member. Sending does not automatically restart a completed agent.
5. **Response reuse.** Per-mission opt-in caches validated pure responses, excluding tool-enabled agents, demo inference and attachments. Keys include messages, content-hashed project files, permissions, source labels, data policy, route, declared model revision and output checks. Unbounded or unreadable project snapshots disable reuse. Imported GGUF identity supplies its local revision. Provider/local/device revisions must be explicitly pinned; mutable cloud aliases cannot be independently verified. TTL and entry ceilings are configurable.
6. **Team rooms.** Private TLS ingress serves project-scoped team APIs. Individual hashed credentials expire and can be revoked. Viewer reads; operator creates/pauses/resumes missions and steers agents; reviewer applies staged artifacts. Custom architectures and tool access require owner project grants. Team operators cannot select private provider profiles directly or opt into public worker sharing. The desktop connects through its local engine with a session credential and optional trusted CA. Owner audit records chain hashes; this is a local tamper-evident chain, not external notarization.
7. **Data destination rules.** Restrict project data to local/private/cloud/public routes, specific profiles/devices and per-file glob rules. Source restrictions follow upstream results, delegated tasks, child swarms and saved/semantic memory. Sensitive-content patterns trigger an interrupted mission and redacted preview before nonlocal model requests or outbound tool arguments. Owner may block, redact or allow the original, then resume. Detection is heuristic and is not exhaustive DLP. Compatible gateways and Exo profiles are conservatively classified as cloud since downstream placement is not independently established.
8. **Failure lab.** Isolated scripted model/worker fixtures inject disconnects, quota errors, invalid output, invalid tools, slow responses, saved-engine reconstruction, stale worker leases and untrusted tool requests. Checks assert containment and checkpoint recovery. They do not interrupt real devices or use provider keys. Engine reconstruction is not an operating-system crash test, and tool-grant containment does not establish broad prompt-injection resistance.
9. **A2A text interoperability.** Owner approves an origin, discovers its Agent Card and grants it to a project. Supports A2A 1.0/0.3 JSON-RPC and HTTP+JSON text send/poll/cancel, same-origin card endpoints, bounded responses and owner-requested SSE task updates. Task IDs remain mission-scoped. Remote-agent free eligibility is an owner declaration. gRPC, tenant-scoped interfaces, multimodal parts and push webhooks are not implemented.
10. **Experimental sharding lab.** An enabled Exo profile can inspect reported topology/memory/models, measure bounded HTTP transfer, request Pipeline/Tensor MLX placement, review it, and deploy that exact short-lived preview. Stop requests target an explicit instance ID. Exo itself must be installed on supported Apple Silicon hosts. Placement feasibility and model execution remain Exo's responsibility. HTTP throughput includes application overhead and does not predict tensor interconnect bandwidth. This is not arbitrary pooling of Windows/Linux GPUs. Normal private workers distribute separate inference jobs across heterogeneous devices.
11. **Signed community registry.** HTTPS index and package envelopes use pinned Ed25519 keys and canonical `swarm-json-v1` sorted compact UTF-8 JSON. The signed index includes exact package SHA-256, versions, expiry and serial; observed rollback is rejected. Preview shows permissions, examples and evaluation declarations. Architectures import as fresh editable records; plugin declarations become disabled drafts requiring executable setup and explicit activation in Extensions. Built-in examples do not claim live-provider quality evaluations. Publisher public keys ship in source; private keys stay in an OS vault/GitHub Actions secrets.
12. **Public releases.** GitHub Actions prepares Windows, Linux and both macOS architecture packages, verifies frozen engines, and uploads release artifacts and a merged updater manifest. Updater artifacts use Tauri signatures. Pages serves signed registry metadata and `updates/stable.json`; installers stay in GitHub Releases. Domain DNS is an owner setup step. Operating system code signing/notarization requires separate real certificate credentials. See PUBLIC_HOSTING.md.
